# 플레이어 상태 머신 (상태 번호·인간↔오징어 전환·벽 붙기·발밑 잉크)

Splatoon 3(v0) 플레이어의 "행동 상태" 번호 체계, 그 번호가 애니메이션 커맨드로 바뀌는 과정, 인간↔오징어 전환 순서, 벽 수영(벽을 지면으로 취급하는 법선 한계 전환), 발밑 잉크 비율 계산(PlayerStepPaint)과 사격 중 이동 속도 연결을 정리합니다. 작업 지침은 [../../분석.txt](../../분석.txt).

관련 문서:
- [movement_physics.md](movement_physics.md) — 속도·가속(이 문서의 상태 집합과 발밑 잉크 비율을 소비)
- [../graphics/anim_state_machine.md](../graphics/anim_state_machine.md) — ASB 파일 구조(상태 이름 = ASB 커맨드 이름)
- [gear_skills.md](gear_skills.md) — PlayerParam 기어 값

상태: **분석 진행 중**(판독 단계). 웹 구현 없음. 상태 번호↔이름은 데이터 대조로 확정, 인간↔오징어 전환·형태 안 전이(0x7102442354) 우선순위와 이동 핵심 상태 선택·오징어 요청 입력 경로를 판독했다(2026-10-02 [move] 3차, 보조 분석 포함). 원본 실행 검증은 없다.

## 1. 개요와 사용자에게 보이는 동작

- 플레이어는 매 프레임 "상태 번호" 하나(0..0x11d, 286개)를 가진다. 상태 번호는 곧 **애니메이션 커맨드 이름**이다(예: 0x45 `WalkHold`, 0x87 오징어 `Walk`). 이동 코드도 이 번호로 인간/오징어 속도 경로를 고른다.
- 상태마다 그 애니를 재생할 모델이 정해져 있다(사람 모델 ASB 또는 오징어 모델 ASB). 번호가 다른 모델 쪽으로 넘어갈 때 **재생하는 ASB(=그려지는 모델 쪽 애니)** 가 바뀐다.
- 오징어 버튼을 누르면 사람 모델이 `ToSquid`(6프레임 클립)를 재생하다가 끝나기 3프레임 전에 오징어 모델 `ToSquid`(13프레임)로 넘어가고, 이어 오징어 `Wait`/`Walk` 등으로 간다. 떼면 오징어 `ToHuman`(3프레임) → 사람 `ToHuman`(30프레임).
- 오징어 상태에서 발밑(또는 벽)이 아군 잉크면 지면 판정 법선 한계가 0.6414(50.1°)에서 −0.2571(104.9°)로 내려가 **벽과 약간 뒤집힌 면까지 지면으로 취급**된다 → 벽 수영.
- 발밑 잉크 비율은 팀별 샘플 개수로 계산하고, 적 잉크 비율은 천천히(최대 1/3씩) 오르고 0.25씩 내려간다. 이동 감속에 쓰는 적 잉크 값은 다시 0.2까지 올라가는 비율로 평활된다.

### 4.1 오징어 상태 집합 [판독]

이동 코드와 상태기계는 이름이 아니라 번호 범위로 판정한다.

| 집합 | 범위 | 사용 |
|---|---|---|
| **S** (이동의 오징어 경로) | 0x82~0x90, 0xaa~0xac, 0xed, 0xee, 0x10c | 0x710245b2b4(오징어 속도), 0x71024abcf0(벽 법선 한계), 0x710268c080/0x710268c3fc |
| **Q** (상태기계의 "지금 오징어") | S ∪ 0xb8~0xba | 0x710243e7d0 (`bVar7`) |

S 의 이름: 0x82 ToSquid(사람), 0x83 ToSquid_Chariot(사람), 0x84 ToSquid(오징어), 0x85 Wait, 0x86 WaitStandby, 0x87 Walk, 0x88 Surprise, 0x89 Jump_St, 0x8a Jump, 0x8b Jump, 0x8c Jump_Ed, 0x8d/0x8e Somersault, 0x8f WallJumpCharge, 0x90 WallJump, 0xaa DokanWarp_St, 0xab DokanWarp_Ar, 0xac DokanWarp_Ed, 0xed PreDive, 0xee Dive, 0x10c CoopWaitEntryCharge. Q 에만 있는 것: 0xb8 Injection_St, 0xb9 Injection, 0xba Injection_Ed(오징어 모델) [데이터: 상태 표].

0x91(오징어 ToHuman)과 0xad(DokanWarp_ToHuman 오징어)는 오징어 모델이지만 S·Q 둘 다 아니다 → 이 상태에서는 이미 인간 속도 경로를 탄다 [판독].

> 정정(movement_physics.md §4.2): "상태 번호와 이름 대응을 찾지 못했다"는 이 표로 해소됐다. 집합 S 자체는 그대로 맞다.
>
> 비트 0·16·19 읽는 코드 검색 범위: 0x710243c000~0x7102460000, 0x7102630000~0x7102640000, 메인 계산, 슬롯19, 상태 표 참조 34곳 전부 [판독].

## 5. 상태 변경 함수

### 5.1 요청 0x7102447bfc(rate, SM, state, a, force) [판독]

인자: s0 = 재생 속도(대부분 1.0), x0 = SM, **w1 = 새 상태**, w2 = 플래그 a(블렌드 0 강제), w3 = force(조건 무시).

> 정정(이전: "w2 = 새 상태, w3 = a, w4 = force"): 명령 판독 결과 레지스터가 한 칸씩 앞이다(x0 = SM). 디컴파일 시그니처 `(rate, SM, state, a, force)` 자체는 맞다.

```
e = 표[state]
if state == SM.cur && !force:
    // 같은 상태 재요청: 보조 상태가 0xf(Attack_Rllr_Aerial)이고 0x5e..0x81 이며 특정 무기(id/10*5 == 0x203)이면
    // 보조 슬롯 진행 프레임 + 속도 ≥ 24 일 때만 다시 건다
    ...
wrapper = e.human ? SM+0x08 : SM+0x10
if SM.active != wrapper && state ∉ {0x91..0x98} && state ∉ {0xad,0xae} && state ∉ {0x82,0x83,0x84} && state ∉ {0xf1,0xf2}
   && !(0xe6 ≤ state ≤ 0x11d) && !force:
    return 0                      // 모델이 다른 상태로는 전환 상태를 거치지 않으면 못 간다
(현재 상태 진행 프레임 조건, 0xe6~0x11d 연출 상태의 최소 재생 프레임 95/50/100/15·999 등 검사)
if 전역 [*0x7105790698]+0x120: SM+0x1d4=state, +0x1d8=rate, +0x1dc=a   // 지연
else 0x710244128c(rate, SM, state, a)
return 1
```

### 5.2 적용 0x710244128c(rate, SM, state, a) [판독]

```
e = 표[state]; wrapper = e.human ? SM+0x08 : SM+0x10
if SM.active != wrapper:
    if SM.active: (e.flags & 8) ? SM.active+0x38 = 1 : 0x710244f084(-1, SM.active, 슬롯0)   // 이전 모델 애니 정지
    SM.active = wrapper
(보조 상태 SM+0xd0 와 레이어 플래그 0xe0/0x700 비교 → 상체 레이어 유지 여부 bVar6, uVar12)
(점프 계열 0x99~0xa9: JumpVarID 고르기 — 랜덤 = 래퍼+0x10 %2 +1, 0x9a(JumpShoot_St)는 SM+0x200>0x5a 일 때만)
blend = a ? 0 : *(int*)e.blendPtr
if 사격 관련 조건(0x710246d5fc) && 특정 전환이 아님: blend = 본체+0x4ec>0 ? 8 : (특수 3 + 무기 0xb54 ? 2 : 4)
0x7102451a90(blend, SM.active, state, 레이어유지, …, 0xe6≤state≤0x11d)    // ASB 커맨드 요청
SM.prev = SM.cur; SM.cur = state
0x7102450510(rate, SM.active, 슬롯0)      // 슬롯+0xd4 = 재생 속도
if state == 0x9a: SM+0x200 = 0
```

### 6.3.1 슈터 인간 걷기 재생률과 MoveSpeedRt — 7차 [실행]+[판독]

2026-10-03: 위의 “사람 걷기 재생 속도식과 보조 레이어를 정리하지 않았다”는 기록을 다음 근거로 보완한다. 범위는 **스플래시슈터 K=1, 서브·스페셜 입력 및 대시 패널 효과 없음**이다. 다른 무기의 속도표는 이번 범위 밖으로 남긴다.

원본 경로: `0x7102442354`가 지상 상태와 보조 상태를 고른 뒤 `0x7102445dd0`부터 속도를 계산 → `0x7102446dfc`에서 SM+0xe0 기록 → `0x7102450510`이 AS 슬롯+0xd4에 재생률 기록. AS 블랙보드 `MoveSpeedRt` 공급자는 기존 확인된 `0x710246cb58`이다. **SM+0xe4와 본체 B+0xe4(최종 속도 vec3)는 다른 필드다.**

| 기준 객체·필드 | 값·수명 | writer / reader |
|---|---|---|
| SM+0xd4 | 이동 애니메이션용 스칼라 v | `0x710243e7d0`가 `0x710246d060` 반환값 기록 / 아래 구간 |
| SM+0xe0 | MoveSpeedRt, 매 갱신 평활 누적값 | `0x7102446dfc` / `0x710246cb58` |
| SM+0xe4 | 기본 재생률 배율 **1.25f(0x3fa00000)** | 사람·오징어 래퍼 초기화 `0x710243d01c`의 `0x710243d674~678` / `0x710244671c`, `0x7102446868` |
| B+0x47c | 입력 크기; 0보다 큰지로 ε 선택 | 이동 입력 / `0x7102446608` |
| 활성 AS 슬롯+0xd4 | 해당 슬롯 재생률 | `0x7102450510` / 애니 프레임 전진 |

초기화 함수는 두 래퍼를 연결한 다음 SM+0xe4에 1.25를 무조건 기록한다 [판독]. 이 두 명령을 별도 실행해 기록 비트를 확인했다. 임의 런타임 덮어쓰기가 절대 없다는 주장으로 확대하지 않는다.

슈터의 도달 가능한 지상 이동 상태와 상수 [데이터]+[판독]:

| 상태 | 낮은 속도 a | 중간 속도 b | 빠른 속도 c | 최대 속도 d |
|---|---:|---:|---:|---:|
| 0x5f WalkHold, 0x60 WalkShoot, 0x69 WalkBackShoot | 0.04 | 0.625 | 0.5 | 0.8 |
| 0x72 WalkLeftShoot, 0x7b WalkRightShoot | 0.2 | 0.9375 | 0.7 | 0.9 |
| 0x5e WalkDamage | 아래 별도 식 | — | — | — |

`F`는 매 연산 f32 반올림이다. 이 구간은 fmul/fadd를 따로 수행하며 FMA로 합치지 않는다. `lerp(a,b,t)=F(a+F(F(b−a)×t))`, `ε = B+0x47c>0 ? bits(0x3a83126e) : bits(0x3b449ba6)`이다. 앞의 ε는 보통 소수 0.001로 적는 값보다 1 ulp 작다. 나머지 상수도 도구의 비트값을 사용한다.

```text
factor = SM.e4
if cur ∉ [0x5e, 0x81]:
    SM.e0 = 0
    return                         # AS 재생률은 이 구간에서 바꾸지 않음

blendTarget = 0
if cur == 0x5e:
    t = clamp01(F(F(v−ε) / F(bits(0x3c75c290)−ε)))
    rate = lerp(0.0625, 3.125, t)
elif v < F(0.027):
    t = clamp01(F(F(v−ε) / F(F(0.027)−ε)))
    rate = lerp(a, b, t)
elif v < F(0.05):
    blendTarget = F(F(v + F(-0.027)) / F(0.023))
    rate = F(b + F(blendTarget × F(F(c×factor)−b)))
else:
    t = clamp01(F(F(v + F(-0.05)) / F(F(0.096) + F(-0.05))))
    rate = F(factor × lerp(c,d,t))
    blendTarget = 1
SM.e0 = lerp(SM.e0, blendTarget, F(0.2))
setSlotRate(activeWrapper, 0, rate) # 원본 0x7102450510
```

위 식의 clamp는 원본의 끝점 비교를 간단히 표시한 것이다. 실행 대조용 구현은 나누기 전 끝점 분기를 그대로 지킨다. 기본 factor=1.25에서 v=0.096이면 앞·뒤 재생률은 1.0, 옆 재생률은 1.125다. WalkDamage는 rate에 factor를 곱하지 않으며, MoveSpeedRt 목표도 0이다. 걷기 속도와 블렌드 값은 같은 필드가 아니다.

### 6.3.2 슈터 보조 레이어 선택 — 7차 [실행]+[판독]

`0x710244a260(SM, airFlag)` → 지상 이동 `0x710244ab70`, 정지 `0x710244b030`, 필요 시 NG 판정 `0x710244b190` → 요청값이 −1이 아니면 `0x7102448400`이다. 여기서 `airFlag`는 호출자가 넘기는 인자이며 B+0xc0을 이 함수가 직접 읽는 것이 아니다. 보조 상태를 요청하지 않은 프레임에는 이 함수가 SM+0xd0을 지우지 않는다. 최종 채택·레이어 우선순위는 §5의 요청 적용 경로가 담당한다.

사격장 슈터 K=1, 레일·서브·스페셜 입력 없는 경로:

| 조건 | 요청 |
|---|---|
| 지상 호출, SM+0xd0=0x31 | 유지(요청 없음). 단 0xe2/0xe3 벽 점프 상태는 이 검사 우회 |
| 지상 호출, v<ε 또는 주 상태 0x4c~0x5d | 정지 선택 함수가 −1 반환(요청 없음) |
| 지상 호출, 주 상태 0x5e WalkDamage | 요청 없음 |

벽 점프 종료 0xe3은 v≥ε이면 일반 이동 분기로 이어지고 0x31 유지 검사를 우회한다. 위 표의 지상 정지 분기보다 이 예외를 먼저 적용한다. 이동 v 비교는 엄격한 `<`이므로 v==ε는 이동 쪽이다.

사격 자세 `0x710246d5fc`도 원본 그대로 연결 실행했다. K=1의 이 테스트 경로에서는 B+0xad8와 B+0x4d8이 양수이고 공격 입력 B/C가 없어야 참이다. 액터 컴포넌트 배열이 존재하고 인덱스 0x37의 두 표시 플래그가 모두 꺼져 있으면 그보다 먼저 거짓을 반환한다. 하네스의 액터 컴포넌트 배열은 비워 이 표시 검사를 우회했다.

**NG 판정의 정확한 조건** (`0x710244b190`, 슈터 K=1):

- `L` = 주 상태가 {0x59,0xc2,0xc5}, 또는 보조 상태가 {0x0d,0x12,0x23,0x36,0x38,0x39}, 또는 `SM+0x1fd!=0`이면서 직전 주 상태가 앞 집합 또는 보조 상태가 {0x0d,0x12,0x23,0x36}.
- L이면 해당 AS 슬롯의 **끝 프레임**(`0x710245064c`)이 12보다 작을 때 즉시 거짓. 그렇지 않으면 임계 T=12. L이 아니면 T=3.
- 공격 입력 A=`B+0xab4<1 && (B+0x4d0>0 || B+0x530 || B+0x531)`가 없거나 잉크 충족 판정 `0x71024bb75c`가 거짓이면 NG=true.
- A가 있고 잉크도 충족하면 `0x7102580a74(슈터)` 반환값 Q에 대해 **Q>T**일 때만 true. 같으면 false.
- SM+0x1fd는 주 상태 적용 `0x710244128c`가 1로, 다음 상태기계 갱신 시작 `0x710243e7d0`이 0으로 쓴다 [판독].

검증에서는 끝 프레임·잉크 충족·Q를 경계 입력으로 제공했다. 이 세 소비자 전체를 이번 실행 검증으로 확정한 것이 아니며, 임계 3/12를 사격 간격으로 바꾸어 해석하지 않는다. `0x7102580a74`는 로컬 경로에서 슈터 +0x6c와 정수 +0x74의 큰 값 또는 조건부 999를 돌려주는 기존 함수다. 실제 발사·잉크 수명은 [슈터 문서](../weapon/shooter_bullet.md)의 해당 근거를 따른다.

### 6.3.3 Jump_St의 지상 상태 요청 차단 — 7차 [실행]+[판독]

§6.3 [B]에서 `air<1 → P16`으로 내려간다는 것만으로 새 상태가 즉시 적용되지는 않는다. 원본 `0x7102447bfc`의 요청 검사를 Jump_St(0x99)/Jump_St_Shoot(0x9a)에서 실행했다.

같은 인간 래퍼, 애니가 아직 끝나지 않았고 blend0=force=0인 경우, 현재 프레임 f와 현재 슬롯 재생률 r에 대해 다음과 같다.

| 요청 상태 | 원본 상태 표 bit2 | 허용 조건 |
|---|---|---|
| 0x56 WaitHold, 0x5e WalkDamage, 0x5f WalkHold | 0 | `F(f+r) >= F(7×r)` |
| 0x59 WaitShoot, 0x60 WalkShoot, 0x69/0x72/0x7b | 1 | `F(f+r) > 0` |

따라서 f=0, r=1에서 앞 행은 거부되고 뒤 행은 허용된다. f=6, r=1이면 앞 행도 허용된다. 이것은 “6 게임 프레임 고정 대기”라는 뜻이 아니다. 식은 애니 프레임과 현재 재생률을 사용한다. 애니 종료, blend0=1, force=1 경로는 이 진행 프레임 검사를 우회한다. 실제 Phive 접지 검출과 점프 프레임 전체를 연결 실행한 결과는 아니다.

### 8.1.1 거리 입력의 세계 좌표와 안전 위치 ID — 8차 [판독]+[실행]

2026-10-03 정정: §8.1의 두 위치 의미 미확정을, 안전 위치 원본 writer 및 선택된 접촉 위치의 producer로 보완한다. 현재 액터+0x28c가 세계 발 위치라는 근거는 **기존 6차** `character_controller.md §4.1` write-back을 재사용한다. 이번 신규 근거는 `0x7102643148`의 원본 실행과 `SplResultPlayer→안전 위치`의 실제 대입 명령이다.

`0x7102643148(SafePos*,worldPoint*,u32 bodyID)`는 +0..8에 worldPoint를 그대로, +0x18에 bodyID의 32비트를 기록한다. Ghidra의 세 번째 인자 float 표기는 `str w2`, `cbz w2`, 조회 인자 `mov w1,w2`에 의해 **u32 정수 ID**로 정정한다. ID=0이면 localPoint(+0xc..14)=worldPoint. ID≠0이면 `0x71012db7b4`로 몸체를 찾아 `local=Mᵀ·(world−translation)`을 기록하고, 몸체+0x268에 모델 SRT가 있으면 그 역회전/축척도 적용한다. ID가 유효하지 않으면 worldPoint·ID만 기록하고 기존 localPoint는 남기는 원본 동작이다. SafePos의 앞 vec3과 뒤 vec3을 혼동하면 거리 계산을 잘못한다.

선택된 지지 접촉의 원본 producer `0x7102c5c374..3d4`: 방향 비트가0이면 contact.point(+0) + contact.normal(+0xc)·contact.separation(+0x30), 방향 비트가1이면 contact.point 자체를 Result+0x13e0..13e8에 기록한다. 같은 비트로 반대 몸체(+0x70 또는 +0x78)의 +0x228 ID를 Result+0x13ec에 기록한다. 따라서 이 위치는 **선택된 지지 접촉의 반대 몸체 쪽 세계 접점**이다.

슬롯19 접촉 정리 `0x71024ada10..a58`은 Result+0x13e0 접점과 +0x13ec ID를 SafePos 임시 슬롯(B+0x388)에 기록하고, 지지면·아군 잉크 등 기존 §7.3 gate가 충족되면 A(B+0x350)에 복사한다. 초기화·복귀 경로 `0x7102499890`도 같은 writer로 슬롯들을 채운다. `0x71024b0af8`에서 d는 **현재 세계 발 위치와 SafePos A의 세계 접점 스냅샷** 사이의 거리이며, `SafePos.localPoint` 사이의 거리가 아니다. 벽과 바닥의 임계/거리^4 식은 기존 §8.1 판독을 유지한다. SafePos 전체 복귀 선정 정책은 이 개별 거리 입력 질문보다 넓으며 별도 미확정이다.

writer 원본 실행: ID=0/조회 실패/몸체 역행렬/추가 SRT 역변환 **1,800건·12,600필드 불일치0**(`web/tools/r8_player_ground_safe_emu.py`, `analysis/completion/r8/player_ground_safe_emu.json`). 몸체 ID 조회 응답은 합성, AcquireReadLock/ReleaseReadLock는 빈 스텁이며 실제 세계의 객체 수명·락 경쟁을 실행한 것은 아니다. 이전 6차 액터 write-back 1,024건을 신규 건수로 세지 않는다.
