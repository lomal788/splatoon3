# CPU 입자 중력 — r8 원본 소비 경로

## 1. 기능 개요와 사용자에게 보이는 동작

입자 위치를 먼저 전진시킨 뒤 속도에 중력을 더한다. 이 갱신은 CPU 계산 경로이다. `EmitterData+B5C`는 입자 중력 배율이며 정적 UBO `DC`와 같은 값이라는 기존 데이터 결론에 신규 실제 소비 근거를 연결했다 [판독]+[실행].

## 2. 분석 대상 원본·버전·자료 위치

Splatoon 3 v0 main.reloc.img의 nn::vfx, 기존 `analysis/decomp/vfx/vfx_lib_01.c`. `analysis/assets_work/r6/static.vfxb` 11개 이미터 원본 레코드를 사용한다. 기존 r7 SRT·방향 배율 결과는 재사용하며 새 확정 수에 다시 넣지 않는다.

## 3. 진입점과 전체 호출 흐름

`080ced4` 초기화 중 `080da10..da1c`: `ER+10`의 EmitterData `R+B5C`를 `E+7FC`에 비트 그대로 복사한다. 매 입자 `081c0b8`의 `081cd68` → `08244c4`가 이 필드를 읽는다 [판독]. `08244c4` 전체 함수를 원본 실행하되 `ER+3=0`으로 선택적 필드 후처리를 끈 조건에서 검증했다 [실행].

## 4. 구조체·필드·상수·열거형 표

| 기준 객체 | 오프셋 | 용도 | writer / reader |
|---|---|---|---|
| EmitterData R | B5C | f32 중력 배율 | 원본 데이터 / 080da10 |
| Emitter E | 7FC | 런타임 중력 배율 | 080da18 / 0824560·4584 |
| R | B60/B64/B68 | 중력 방향 xyz | 데이터 / 0824598..45a4 |
| R | B39 | 0이면 방향 그대로, 0 이외면 행렬 변환 | 데이터 / 08245b0 |
| R | A93 | follow 값. 1이면 입자별 축을 정규화 | 데이터 / 08245b8 |
| E | 50 | dt | 기존 r7 시간 경로 / 08244f4 |
| E | 1F8 | 입자 속성 배열. index*10+C를 위치 전진 배율로 소비 | 생성 경로 별도 / 08244e8 |

## 5. 상태 전이와 전체 수명

초기화에서 배율을 복사하고 이후 매 입자 갱신이 소비한다. 매 스텝 위치 계산 → 공기 저항 → 양수 중력 배율 판정 → 중력 더하기 → 선택적 field 순서다 [판독]. 배율이 0·음수·NaN이면 중력 분기를 건너뛴다. 1인 연습 전체 부팅이나 리소스 해제는 이번 검증 범위가 아니다.

## 6. 계산식·조건·상세 의사코드

```text
Pout = pin + vin * f32(dt * attr1.w)   // 각 곱·덧셈은 개별 f32
Vout = air==1 ? vin : vin*powf(air,dt)
if scale>0:
    g = f32(scale * direction)       // xyz 각각
    if B39==0: a=g
    elif A93==1:
        // 입자 행렬의 3개 열: 각각 별도로 정규화
        m = sqrt(f32(f32(z*z + x*x) + y*y))
        col = m>0 ? col*f32(1/m) : (0,0,0)
        a[i] = fma(col[i].z,g.z,fma(col[i].y,g.y,f32(col[i].x*g.x)))
    else:
        a[i] = fma(row[i].z,g.z,fma(row[i].y,g.y,f32(row[i].x*g.x)))
    Vout.xyz = f32(Vout.xyz + f32(a*dt))
    Vout.w = 0
```

位置 전진은 갱신 전 속도를 사용한다. 중력 분기를 건너뛰면 속도 w를 0으로 바꾸지 않는다 [판독]+[실행]. air≠1의 SDK powf 수치 자체는 실행 비교하지 않았으며 호출과 순서를 [판독]으로만 확정했다. ARM `FCMP` 뒤 B.GT/B.LE는 unordered에서도 중력 분기를 건너뛴다. 최초 검증에서 NaN이 진입한다고 잘못 해석한 기대값이 실패했고 NZCV 조건을 다시 판독해 수정했다.

## 7. 애니메이션·이펙트·소리·카메라·에셋 연결

색·크기·텍스처 계산은 별도 경로다. 이 CPU 중력 결과를 GPU 분석적 궤적 전체와 동일하다고 승격하지 않는다. 원본 11개 이미터의 B5C·B39·A93 입력 비트는 결과 JSON에 기록했다 [데이터].

## 8. 다른 기능과의 상호작용

추가 중력·자기장·소용돌이 등의 field는 기본 속도 갱신 이후다. `ER+3=0`으로 이번 실행에서 제외했다. 매트릭스 생산은 기존 follow 분석과 별도 질문이다.

## 9. 웹 포팅 구조와 구현 순서

`impl/fx.md`·`impl/assets.md`의 향후 구현에서 원본 CPU 경로를 선택할 때 dt·입자 전진 배율·air·중력 배율을 분리하고 위치 먼저/속도 나중 순서를 유지한다. 웹 권장 이름 `gravityScaleCpu`=R+B5C, `gravityDirectionCpu`=R+B60. 행렬을 통째로 정규직교화하지 말고 열별 정규화와 0길이 처리, FMA 수치를 보존해야 한다. 이번 작업에서는 웹 코드와 impl을 수정하지 않았다.

## 10. 검증 코드·실행 결과·기대값

`web/tools/r8_fx_gravity_emu.py` → `analysis/completion/r8/fx_gravity_emu.json`. 원본 inline 복사 2,315/2,315, 원본 전체 consumer 2,315건의 18,520개 f32 값 비트 일치, 불일치 0. 11개 원본 레코드 포함, 나머지는 합성 행렬·입자 입력이다. 원본 명령 패치·callee 스텁 없음. air=1, field 꺼짐 조건. 첫 실행 NaN 기대값 AssertionError(exit1), ARM 조건 해석 수정 후 exit0. 포지션·속도 xyz/w와 복사 비트를 비교했다. 실제 GPU 렌더 프레임 실행은 아니다.

## 11. 미확정 사항과 추가 분석에 필요한 근거

r7 고정 inventory `effect_resources.md:L153`의 B5C CPU 소비 질문은 해소했다. 전체 VFXB 필드 질문 L358·L17은 미확정 유지한다. air≠1 SDK powf 비트 실행, 추가 field, 행렬 생산 전체 수명, GPU와의 경로 선택은 각 원래 질문에서 계속 추적한다.
