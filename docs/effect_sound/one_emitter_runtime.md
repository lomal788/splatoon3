# OneEmitter 인스턴스 큐·파티클 용량 — 2026-10-03 r9

## 1. 기능 개요

슈터 탄과 착탄 효과는 한 이미터셋에 여러 위치/행렬 레코드를 넣는다. 인스턴스 큐 길이와 이미터의 파티클 용량은 서로 다른 수다. 원본은 용량 부족 시 레코드를 생략하며 큐를 자동으로 늘리지 않는다.

## 2. 자료와 이전 분석 확인

기존 SHARED/FUNCS/decomp_index의 137F020/137F144/18B2CC0/18B3348과 SDK 소스를 재사용했다. 새 함수는 137F558(256B), 137F4BC(156B)이고 func_lookup 실제 시작을 확인한 후 full_decomp했다. 소스: analysis/decomp/r9_fx/one_emitter_create.c, one_emitter_ready.c, 기존 vfx/vfx_b1.c·vfx_b2.c·vfx_lib_01.c. 기존 읽기를 새 함수 판독 건수로 세지 않는다.

## 3. n/count 정의 [판독]

137F020(slot,n,heap)은 slot+50=n, +58=n×0x60 버퍼다. 137F144(slot,name,count,0)은 SDK 0836100의 x5=count, x6=n, x7=buffer로 전달하며 생성 뒤 slot+14=count를 저장한다. 0836100은 **n≤count**일 때만 생성하고 S+280=buffer, S+288=n, S+3D=1로 둔다. count는 0835EC8→0816044의 인자 구조+0→S+6C→08162D0→08164E4(x2=count)→080CA78의 인자+20→각 E+24로 전달되는 **이미터별 최대 파티클 수**다. E+2C는 CPU 계산 이미터의 현재 파티클 수이며 다음 생성량과 합쳐 E+24에 비교한다. n은 **한 번의 큐 처리까지 수집할 최대 인스턴스 레코드 수**다. 슈터 원본 n40/count100을 "탄 100발" 또는 "매 탄 40파티클"로 해석하지 않는다. 이 할당·생성 상위 경로는 판독이며 실행하지 않았다.

## 4. 큐에 넣기 전 슬롯 판정 [판독]+[실행]

137F558은 slot+8 핸들이 존재하고, 핸들[0]=S가 0이 아니며 핸들+8 generation=S+54일 때 137F4BC를 호출한다. 각 CPU(calcType R+A92=0) 이미터에 대해 `slot+14 < E+2C + trunc_f32(S+7C * R+B48)`이면 0을 돌려 생략한다. GPU 계산 이미터는 이 CPU 용량 검사를 건너뛴다. 통과하면 S+3A=1, S+10 bit0=1, slot+10=0으로 두고 아래 큐 writer를 부른다. 레코드 큐가 가득 찬 경우에도 이 활성화 기록은 일어난다.

## 5. 인스턴스 0x60 B 레코드 [판독]+[실행]

| 오프셋 | 형식·기록값 |
|---|---|
| 00..3F | f32×16. 입력 행 우선 Mat34[12]를 `(m0,m4,m8,0), (m1,m5,m9,0), (m2,m6,m10,0), (m3,m7,m11,0)`로 바꾼 네 vec4 |
| 40/44/48 | f32 1/1/1 |
| 4C | f32 0 |
| 50 | u64 호출자 token/key 원형. 탄 경로는 핸들 generation/index 배치를 치환한 값을 사용 |
| 58 | f32 S+7C, 이번 인스턴스 방출에 쓰는 시간/배율 |
| 5C | u8 1: 전체 행렬 writer(0817B28). 위치만 받는 08179D8은 0을 쓴다 |
| 5D..5F | 이 writer는 쓰지 않는다. 패딩/공식 필드 이름은 원본 근거 없음 |

위 이름 없는 칸을 추측으로 color라고 부르지 않는다. 값과 소비 경로를 원본 오프셋으로 기록한다. 0817B28은 S+3D가 0이 아니고 signed S+28C<S+288일 때만 큐를 쓴다. 연결된 CPU 이미터 중 `E+24 < E+2C + trunc_f32(f32(f32(E+64 * S+7C) * rate))`가 하나라도 있으면 생략한다. rate는 080EED8의 원본 volume/shape 판정에 따라 E+79C 또는 R+B48이다. 허용 시 버퍼[S+28C]를 쓰고 S+28C를 1 늘린다.

## 6. 레코드 소비·리셋 [판독]

081C0B8의 OneEmitter 분기는 S+28C개를 stride60으로 순회하고, 레코드+58을 시간/방출 배율에 곱해 원본 birth thunk081E070에 레코드 포인터를 넘긴다. 08168F0은 이미터 갱신 뒤 S+3D!=0, dt>0, S+28C>0이면 **최대 n개의 레코드+50 token을 모두 0으로 지우고 S+28C=0**으로 둔다. dt≤0이면 이 리셋을 하지 않는다. 파티클 수 count와 인스턴스 큐 n을 구분하는 추가 소비 근거다. 이번 실행에서는 전체 birth/프레임/GPU를 돌리지 않았다.

## 7. 원본 실행 검증 [실행]

`PY web/tools/r9_fx_one_emitter_emu.py`는 137F558→137F4BC→0817E40/08178B0/080EBE4→0817B28/080EED8을 원본 그대로 LR까지 실행한다. 2,048개의 행렬·generation·큐 용량·CPU/GPU·파티클 용량·시간/배율 조합에서 레코드 전체 바이트, 큐 count, 활성화/슬롯 기록을 독립 판독식과 비교했다. 추가293건, 불일치0, 호출 스텁0, unknown PLT0. 출력 analysis/completion/r9/fx_one_emitter_emu.json. float 곱은 f32 각각이며 FMA로 바꾸지 않는다.

## 8. 미확정과 다음 근거

전체 게임 프레임 실행, E+2C 실제 파티클 생명주기, birth 이후 token 추적·각 레코드 40..4C의 GPU 의미와 픽셀 출력은 별도 미확정이다. 다음: 080CA78/080CED4 전체 원본 할당, 081E070/081A6F0/08244C4의 필드 consumer. 원본 이름이 없는 5D..5F를 임의 의미로 채우지 않았다. **큐 레이아웃·n/count 질문은 위 producer/consumer로 해소했지만 VFX 전체 질문은 승격하지 않는다.**

## 9. 웹 반영 필요

impl/fx.md의 용량을 `n=프레임 큐 레코드 한도`, `count=이미터별 파티클 용량`으로 구분하고, 용량 초과·generation 불일치의 원본 생략, 두 admission 단계 및 행렬 전치를 적용할 필요가 있다. 코드와 impl은 변경하지 않았다.

## 10. 명령과 한계

SHARED/FUNCS/index 확인→func_lookup→`sh web/tools/full_decomp.sh analysis/decomp/r9_fx/one_emitter_create.c 0x710137f558`, 같은 방식 137F4BC→원본 실행. 디컴파일 모두 성공, 에뮬레이터2048/2048 성공. 메모리 입력은 합성 슬롯/셋/이미터다. 원본 함수의 실행을 실제 리소스 로딩·Havok·NVN 화면 실행으로 확대하지 않는다.

## 11. 정정 기록

2026-10-03 r9: effect_resources §3의 “n과 count 의미는 이름 없어 추정”을 정정한다. 공식 이름을 추측해 채운 것이 아니라 실제 생성 인자→E+24와 큐 capacity→레코드 writer/consumer를 따라 의미를 확정했다. 기존 문장과 n40/count100 데이터는 이력으로 보존한다. 0x60의 5D..5F는 미기록이라는 원본 결과를 그대로 남긴다.
